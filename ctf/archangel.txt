   maintenant, j'ai du faire un peu de recherche :
   En ce qui concerne l'astuce fournie par THM, elle indique que pour
   exploiter la vulnérabilité LFI, il est nécessaire de visualiser le code
   source du fichier PHP. Comme nous le savons déjà, il n'est pas possible
   de voir le code source de PHP à moins d'être administrateur ou d'avoir
   une mauvaise configuration du côté du serveur.

   J'ai donc cherché sur Google comment voir le code source de PHP en
   exploitant la vulnérabilité LFI. Après quelques minutes, j'ai trouvé
   une information concrète. Il existe des Wrappers intégrés en PHP, qui
   sont responsables de la gestion des tâches liées au protocole, comme le
   téléchargement de données à partir d'un serveur web ou ftp, et de leur
   exposition de manière à ce qu'elles puissent être gérées avec les
   fonctions de flux de PHP.

   L'un de ces blogs explique comment utiliser l'un de ces wrappers pour
   lire le code de PHP à l'aide de LFI.

   PHP:// est un wrapper qui permet d'accéder à différents flux
   d'entrées/sorties. Nous utiliserons php://filter - il s'agit d'une
   sorte de méta-enveloppe conçue pour permettre l'application de filtres
   à un flux au moment de l'ouverture. Il y a plusieurs paramètres à ce
   wrapper, nous utiliserons convert.base64-encode/resource= - Cela
   convertira le fichier donné en encodage base64 et l'imprimera à
   l'écran. Mais nous devons fournir la ressource que nous voulons lire
   comme un nom de fichier index.php.

   Comme nous savons déjà qu'il y a un fichier dans
   /var/www/html/development_testing/ qui est mrrobot.php, essayons ce
   wrapper sur lui.

   et avec cette URL :
   http://mafialive.thm/test.php?view=php://filter/convert.base64-encode/r

   Encore de la recherche :
   "
   Très bien, nous avons le deuxième drapeau générique et le code php. Le
   code dit (si j'ai bien compris) que la première condition est que le
   paramètre que nous passons ne doit pas contenir la chaîne "../../" et
   qu'une autre condition est que le paramètre doit contenir la chaîne
   "/var/www/html/developing_testing". C'est à cause de cette première
   condition que nous avons utilisé la technique "..//..//..//" pour la
   contourner. Ainsi, lorsque ces deux conditions sont remplies, nous
   pouvons exploiter la LFI et obtenir un shell inversé.

   J'ai regardé la section hint, il y est question de "poison". J'ai
   cherché LFI Poison sur Google et j'ai découvert la technique du "Log
   Poisoning". Il y a plusieurs façons d'obtenir un shell inversé via
   l'empoisonnement de logs. Mais, pour cette pièce, nous nous en
   tiendrons à "Apache Log Poisoning".
   "
